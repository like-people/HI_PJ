# 협업 규칙 합의문 (2팀)

공고문의 개발 규칙과 `docs/작업방식.md` 에 더해, 팀이 함께 지키기로 한 규칙이다.

## 1. 담당 표시

공통 모듈과 공동 작업 파일은 여러 사람이 함께 고친다. 누가 채우고 관리하는 부분인지 코드와 기록에서 바로 보이도록 표시한다.

### 1-1. 코드 안 표시

| 무엇을 | 어디에 | 표시 형 식 | 예 |
|---|---|---|---|
| 공통 함수를 채우거나 새로 만들 때 | `def` 바로 윗줄 주석 | `# 담당: 기능 N(이름)` | `# 담당: 기능 4(김영광)` |
| 자료 항목(`store.py` 의 `EMPTY`)을 더할 때 | 그 줄 끝 주석 | `# 기능 N: 설명` | `"locks": [],  # 기능 4: 확정 기간 {"start", "end"}` |
| 지출 항목 안에 필드를 더할 때 | `EMPTY` 의 `expenses` 주석 | `필드(기능 N)` | `"weights"(기능 4)` |
| 공동 작업 파일(`cli.py`, `config.py`, `log.py` 등) | 파일 첫머리 설명 | `담당: 공동 작업 이름(이름)` | `담당: 로그(이름)` |
| 공동 작업이 다른 파일의 일부만 채울 때 | 그 함수의 `def` 바로 윗줄 주석 | `# 담당: 공동 작업 이름(이름)` | `Store.save` 위에 `# 담당: 자료 파일 손상 대응(이름)` |

```python
# 담당: 기능 4(김영광)
def is_locked(store, on):
    """정산이 확정된 기간에 속하는 날짜인가. 담당: 기능 4"""
    ...
```

- 담당은 함수를 열자마자 보이도록 `def` 윗줄에 둔다. 함수 설명(docstring)의 첫 줄은 함수가 하는 일을 적는 자리이므로 담당 표시를 넣지 않는다.
- 스켈레톤이 함수 설명 끝에 적어 둔 `담당: 기능 N` 은 지우거나 옮기지 않고 그대로 둔다.
- 기능 파일(`moim/features/*.py`)과 명령 파일(`moim/commands/*.py`)은 파일 전체가 한 사람 담당이므로 첫머리 설명에 이름만 적는다.
- 남의 담당 부분을 고쳤으면 코드의 담당 표시는 바꾸지 않는다. 관리 책임은 원래 담당자에게 있다. 고친 사람은 PR 설명에 남긴다(1-3).

### 1-2. 커밋 메시지

`docs/작업방식.md` 의 `종류: 한 줄 요약` 형식 그대로 쓴다. 담당은 넣지 않아도 된다(커밋 작성자로 누가 했는지 남는다).

```
feat: queries.is_locked 구현
```

- 넣고 싶으면 `feat(기능4): queries.is_locked 구현` 처럼 괄호로 덧붙여도 된다.

### 1-3. 병합 요청(PR)

- 제목: 커밋 메시지와 같은 형식
- 설명 맨 위에 아래 표를 넣는다.

```
| 항목 | 내용 |
|---|---|
| 담당 | 기능 N(이름) 또는 공동 작업 이름(이름) |
| 바꾼 공통 모듈 | 파일과 함수·자료 항목 (없으면 "없음") |
| 쓰는 기능 | 바꾼 공통 함수를 쓰는 기능 번호 (없으면 "없음") |
| 남의 담당 부분 수정 | 없음 / 있음: 파일·함수, 원래 담당자, 그 담당자의 승인 여부 |
```

- 표 아래에 무엇을 바꿨는지, 왜 바꿨는지 적는다. 검사 결과는 PR 화면의 `check` 에 나오므로 따로 적지 않는다.
- 남의 담당 부분을 고쳤으면 그 담당자를 검토자로 지정하고 승인을 받는다.

#### 병합 요청 예시

제목: `feat: queries.is_locked 구현, store 에 locks 항목 추가`

```markdown
| 항목 | 내용 |
|---|---|
| 담당 | 기능 4(김영광) |
| 바꾼 공통 모듈 | moim/common/queries.py `is_locked`, moim/common/store.py `EMPTY["locks"]` |
| 쓰는 기능 | 1(지출 추가·수정·삭제 거부), 6(가져오기 거부) |
| 남의 담당 부분 수정 | 없음 |

## 무엇을 바꿨나
- `store.py` 의 `EMPTY` 에 확정 기간 목록 `"locks": []` 를 더했다. 한 항목은 `{"start": "YYYY-MM-DD", "end": "YYYY-MM-DD"}`
- `queries.is_locked(store, on)` 를 채웠다. 날짜가 확정 기간 어느 하나에 들어가면 True
- 기간 판정은 `dates.in_period` 를 써서 시작일·끝일을 모두 포함한다(규약.md 3절)
- 테스트 `tests/test_settle.py` 추가: 잠금 없음 → False / 2026-11-01~11-30 잠금에서 11-01·11-15·11-30 → True, 10-31·12-01 → False

## 왜
- 기능 1의 `ledger.insert` 와 지출 수정·삭제가 확정 기간을 막으려면 이 함수가 있어야 한다(규약.md 6절)
- 구현순서 문서 1단계의 바닥 공통 함수

## 검토해 줄 것
- 시작일·끝일 포함이 규약.md 3절과 맞는지
- 옛 자료 파일(locks 없음)을 읽어도 오류가 나지 않는지
```

## 2. 공고문 개발 규칙 (그대로 지킨다)

- 한 PR에 한 가지 변경만 담고 300줄 이하로 한다. 기능을 추가하면 그 테스트를 같은 PR에 넣는다.
- 공통 모듈을 바꾸는 PR은 무엇을 왜 바꿨는지, 어느 기능이 쓰는지 설명에 적는다.
- 검토 의견에는 확인한 내용(실행한 명령과 결과, 규약 값과 대조한 줄)을 적는다. "확인했습니다"만 적은 검토는 검토 건수에 넣지 않는다(필수·선택 기준과 예시는 3절).
- 1인당 다른 사람의 PR을 5건 이상 검토하고, 공통 모듈 PR을 2건 이상 올린다.
- 다른 사람이 맡은 기능 파일은 그 담당자의 승인 없이 고치지 않는다. 충돌을 풀 때 다른 사람의 변경을 지우지 않는다.
- 잘못 병합한 것은 `git revert` 로 되돌린다. force push 와 기록 삭제는 금지다.

## 3. 검토

- 검토 요청과 승인은 `docs/작업방식.md` 3절(6·7번)대로 한다.
- 승인할 수 있는 사람은 `docs/역할.md` 의 저장소 관리 표대로다.
- 검토 요청을 받으면 3시간 안에 답한다. 밤 12시부터 아침 9시 사이에 받은 요청은 3시간 안에 답하지 않아도 되고, 그날 낮 12시까지 답한다.
- 3시간 안에 답할 수 없으면 요청한 사람에게 미리 알린다.
- 요청받은 사람과 연락이 닿지 않으면 관리자 2명(dudrhkd, seolbinga)에게 연락한다.

### 검토 의견 예시

검토 의견에는 확인한 것을 하나 이상 구체적으로 적는다. "확인했습니다"만 적은 검토는 검토 건수에 넣지 않는다(공고문).

- **필수**: 코드를 읽고 규약·요구사항과 대조한 줄을 적는다.
- **선택**: 브랜치를 받아 직접 실행한 명령과 결과를 적는다. 테스트는 `check` 가 이미 돌리므로, `check` 가 보지 못하는 것(명령 출력, 옛 자료 파일 등)을 볼 때 쓴다.

위 1-3의 병합 요청 예시를 검토한 경우:

```markdown
## 확인한 것
- 규약.md 3절 "기간은 시작일과 끝일을 모두 포함" ↔ queries.py `is_locked` 가 `dates.in_period` 를 씀 → 일치
- 경계값: 11-30(끝일) True, 12-01 False 테스트가 있음
- store.py `_check_shape` 가 없는 항목을 EMPTY 기본값으로 채우므로 locks 가 없는 옛 자료 파일도 읽힘

## 의견
- 기능 1(`ledger.insert`)에서 바로 쓸 수 있는 형태라 문제 없음. Approve
```

직접 실행까지 했으면 `확인한 것` 에 덧붙인다(선택):

```markdown
- 브랜치를 받아 실행: 옛 data.json(locks 없음)으로 `Store(...).load()` → 오류 없음, locks 는 []
```

- 고칠 점이 있으면 Approve 대신 Request changes 로 남기고, 어느 줄이 왜 문제인지 적는다.
